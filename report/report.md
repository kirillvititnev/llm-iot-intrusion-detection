# Использование российских LLM для генерации Python-приложения анализа IoT-трафика

## 1. Постановка задачи

Цель работы — проверить, можно ли использовать большие языковые модели для генерации Python-приложений, которые решают прикладную задачу анализа сетевого трафика. В качестве предметной области была выбрана классификация IoT-трафика по датасету **IoT Intrusion Detection Dataset**.

Основной исследовательский вопрос формулируется так: может ли LLM по текстовой подсказке сгенерировать рабочий и воспроизводимый ML-пайплайн для классификации нормального и вредоносного сетевого трафика, и насколько такой результат сопоставим с реализацией, написанной вручную.

В рамках эксперимента сравнивались три подхода:

1. ручная baseline-реализация на Python;
2. приложение, сгенерированное YandexGPT;
3. приложение, сгенерированное GigaChat.

Для YandexGPT и GigaChat использовался один и тот же русскоязычный промпт. После первого запуска фиксировались ошибки, затем LLM получали уточняющие промпты для исправления собственного кода. Такой подход позволил оценить не только качество финального ML-решения, но и способность моделей участвовать в итеративной отладке.

## 2. Описание датасета

В работе использовался датасет **IoT Intrusion Detection Dataset** с Kaggle. В локальном проекте файл датасета называется `IoT_Intrusion.csv` и расположен в папке `data/raw/`.

После загрузки датасета были получены следующие характеристики:

- количество строк: **1 048 575**;
- количество столбцов: **47**;
- количество признаков: **46**;
- целевой столбец: **`label`**;
- количество пропусков: **0**;
- тип задачи: **многоклассовая классификация**.

Целевой столбец `label` содержит классы нормального и вредоносного трафика. В датасете присутствуют как крупные классы, например `DDoS-ICMP_Flood`, `DDoS-UDP_Flood`, `DDoS-TCP_Flood`, так и редкие классы, например `Uploading_Attack`, `XSS`, `Backdoor_Malware`, `Recon-PingSweep`.

Эта особенность важна для интерпретации результатов: датасет сильно несбалансирован. Поэтому обычная accuracy может выглядеть высокой даже в ситуации, когда модель плохо распознает редкие классы. В связи с этим основной метрикой сравнения был выбран **macro F1-score**.

## 3. Методология эксперимента

Эксперимент был построен как сравнение трех вариантов реализации одной и той же задачи.

На первом этапе был создан единый промпт для LLM. В нем задавались требования к будущему приложению:

- загрузить CSV-файл из папки `data/raw/`;
- определить целевой столбец;
- провести первичный анализ данных;
- выполнить предобработку признаков;
- обучить несколько моделей машинного обучения;
- рассчитать accuracy, precision, recall и F1-score;
- сохранить результаты и лучшую модель;
- оформить решение как запускаемый Python-файл.

На втором этапе этот промпт был передан двум российским LLM: **YandexGPT** и **GigaChat**. Полученные ответы сохранялись в папке `prompts/`, а сгенерированный код переносился в папку `src/`.

На третьем этапе был реализован ручной baseline. Он нужен как контрольная точка: с ним сравнивались результаты LLM-сгенерированных программ.

На четвертом этапе все варианты были запущены локально на одном датасете. Для каждой реализации фиксировались:

- запустился ли код с первой попытки;
- какие ошибки возникали;
- какие уточняющие промпты потребовались;
- какие модели были обучены;
- какие метрики были получены.

Такой формат позволяет оценить LLM не только как генератор кода, но и как инструмент, который должен создавать воспроизводимое приложение для анализа данных.

## 4. Использованные LLM

В эксперименте использовались две российские LLM:

1. **YandexGPT 5 Pro**;
2. **GigaChat**.

Обеим моделям передавался один и тот же русскоязычный промпт. Это важно для корректного сравнения, поскольку различия в результатах связаны не с разной постановкой задачи, а с тем, как каждая модель интерпретировала одинаковые требования.

В работе также был подготовлен англоязычный вариант промпта, однако основной эксперимент проводился именно на русскоязычной подсказке, так как одной из задач было проверить применимость российских LLM в русскоязычном сценарии.

## 5. Исходный промпт

Исходный промпт был составлен так, чтобы LLM получила не общую просьбу «написать модель», а конкретное техническое задание на Python-приложение.

В промпте были явно зафиксированы:

- роль модели: Python-разработчик и специалист по машинному обучению;
- предметная область: анализ сетевого трафика;
- источник данных: локальный CSV-файл из `data/raw/`;
- ожидаемые этапы пайплайна;
- список моделей машинного обучения;
- набор метрик;
- требования к сохранению результатов;
- ограничения, связанные с утечкой данных и воспроизводимостью.

Полный текст исходного промпта находится в файле:

```text
prompts/prompt_ru.md
```

Ответы LLM и последующие уточняющие промпты сохранены в папке `prompts/`.

## 6. Ручная baseline-реализация

Ручная реализация была написана как контрольный вариант. Она не использовалась как «идеальное» решение, но позволила получить понятную точку сравнения для LLM-сгенерированного кода.

В ручном пайплайне были реализованы следующие этапы:

- автоматический поиск CSV-файла в `data/raw/`;
- загрузка датасета;
- автоматическое определение целевого столбца `label`;
- вывод размера датасета и распределения классов;
- разделение данных на признаки и целевую переменную;
- кодирование целевой переменной;
- разделение на train/test;
- обработка пропусков;
- масштабирование числовых признаков;
- обучение моделей Decision Tree и Random Forest;
- расчет accuracy, precision macro, recall macro и F1 macro;
- сохранение отчетов, confusion matrix и лучшей модели.

Результаты ручной реализации:

| Модель | Accuracy | Precision macro | Recall macro | F1 macro |
|---|---:|---:|---:|---:|
| Decision Tree | 0.9928 | 0.8305 | 0.8297 | 0.8294 |
| Random Forest | 0.9932 | 0.8095 | 0.7247 | 0.7369 |

Формально Random Forest показал немного более высокую accuracy, однако по основной метрике macro F1 лучшей моделью стала **Decision Tree**. Это ожидаемо для несбалансированного датасета: accuracy хорошо отражает качество на крупных классах, но хуже показывает проблемы с редкими атаками.

## 7. Результаты YandexGPT

YandexGPT сгенерировала код, который в целом соответствовал требуемой структуре ML-пайплайна. В нем присутствовали загрузка данных, первичный анализ, предобработка, обучение моделей и расчет метрик.

Однако код не запустился с первой попытки.

### 7.1. Первая ошибка

На первом запуске возникла ошибка:

```text
FileNotFoundError: [Errno 2] No such file or directory: 'data/raw/IoT_Intrusion_Detection_Dataset.csv'
```

Причина была в том, что модель указала в коде конкретное имя CSV-файла `IoT_Intrusion_Detection_Dataset.csv`, хотя реальный файл в проекте назывался `IoT_Intrusion.csv`.

Для исправления был отправлен уточняющий промпт с требованием не использовать жестко заданное имя файла, а автоматически находить первый CSV-файл в папке `data/raw/`.

### 7.2. Ошибка выбора лучшей модели

После исправления пути к файлу код смог загрузить датасет, но завершился новой ошибкой на этапе выбора лучшей модели:

```text
KeyError: 'accuracy'
```

Ошибка была связана с тем, что функция оценки моделей возвращала словарь метрик не в той структуре, которую ожидала функция сохранения лучшей модели. После следующего уточняющего промпта модель изменила логику, но возникла еще одна похожая ошибка:

```text
KeyError: 'f1'
```

Фактически проблема заключалась не в машинном обучении, а в несогласованности структуры словаря метрик. Код считал метрики, но затем пытался обратиться к ним по неверному ключу или на неверном уровне вложенности.

### 7.3. Финальный запуск YandexGPT

После точечного промпта для исправления функции `save_best_model()` код YandexGPT успешно выполнился до конца.

Финальная версия выполнила:

- загрузку `IoT_Intrusion.csv`;
- автоматическое определение целевого столбца `label`;
- первичный анализ данных;
- предобработку признаков;
- обучение Random Forest, Logistic Regression и Decision Tree;
- расчет метрик;
- сохранение результатов;
- выбор лучшей модели по macro F1-score.

Во время обучения Logistic Regression появилось предупреждение `ConvergenceWarning`: модель не успела сойтись за 1000 итераций. Это не остановило выполнение программы, но показывает, что Logistic Regression не является самым удачным вариантом для такого большого многоклассового датасета без дополнительной настройки.

Результаты финальной версии YandexGPT:

| Модель | Accuracy | Precision macro | Recall macro | F1 macro |
|---|---:|---:|---:|---:|
| Random Forest | 0.9932 | 0.8110 | 0.7213 | 0.7314 |
| Logistic Regression | 0.8453 | 0.6407 | 0.5203 | 0.5381 |
| Decision Tree | 0.9930 | 0.8455 | 0.8384 | 0.8399 |

Лучшей моделью стала **Decision Tree** с macro F1-score **0.8399**.

## 8. Результаты GigaChat

GigaChat также сгенерировал Python-приложение для решения задачи классификации IoT-трафика. Как и в случае с YandexGPT, первый вариант кода не был полностью рабочим.

### 8.1. Первая ошибка

На первом запуске возникла ошибка:

```text
FileNotFoundError: Файл data/raw/IoT_Intrusion_Detection_Dataset.csv не найден.
```

Причина совпала с первой ошибкой YandexGPT: модель жестко указала имя файла, которого не было в проекте.

После уточняющего промпта код был исправлен: программа стала автоматически искать CSV-файл в папке `data/raw/`.

### 8.2. Ошибка определения целевого столбца

После исправления загрузки файла GigaChat допустил другую ошибку. Код не смог корректно определить целевой столбец и предложил выбрать один из бинарных признаков сетевого трафика, например `HTTP`, `TCP`, `UDP`, `ICMP`.

Причина заключалась в функции определения target column: GigaChat пытался выбрать целевой столбец по количеству уникальных значений и отбирал признаки, где `unique_vals <= 10`. Для данного датасета такая логика некорректна, потому что целевой столбец `label` содержит больше 10 классов.

После второго уточняющего промпта функция определения целевого столбца была исправлена: сначала код стал искать столбцы с названиями `label`, `class`, `attack`, `attack_type`, `category` и только после этого переходить к ручному выбору.

### 8.3. Финальный запуск GigaChat

В обновленной версии у GigaChat были обучены три модели:

- Random Forest;
- Logistic Regression;
- Decision Tree.

Финальная версия выполнила программу до конца и сохранила результаты в файл:

```text
results/gigachat_metric_2s.txt
```

Во время выполнения появились предупреждения `ConvergenceWarning` и `UndefinedMetricWarning`. Первое связано с тем, что Logistic Regression не сошлась за 1000 итераций. Второе показывает, что некоторые редкие классы не были предсказаны отдельными моделями ни разу. Для данного датасета это ожидаемо из-за сильного дисбаланса классов.

Результаты финальной версии GigaChat:

| Модель | Accuracy | Precision macro | Recall macro | F1 macro |
|---|---:|---:|---:|---:|
| Random Forest | 0.9930 | 0.8090 | 0.7250 | 0.7370 |
| Logistic Regression | 0.8460 | 0.6390 | 0.5240 | 0.5410 |
| Decision Tree | 0.9930 | 0.8310 | 0.8300 | 0.8290 |

После включения Decision Tree лучшей моделью GigaChat-версии стала **Decision Tree** с macro F1-score **0.8290**.

Это важное изменение относительно промежуточного запуска, где GigaChat обучал только Random Forest и Logistic Regression. В промежуточной версии лучшей моделью был Random Forest с F1 macro 0.7370, но после добавления Decision Tree результат GigaChat стал сопоставим с ручной baseline-реализацией.

## 9. Сравнение результатов

Сравнение проводилось по двум направлениям:

1. техническая корректность кода;
2. качество моделей по метрикам классификации.

Итоговая сравнительная таблица:

| Подход | Лучшая модель | Код запустился сразу | Accuracy | Precision macro | Recall macro | F1 macro | Комментарий |
|---|---|---:|---:|---:|---:|---:|---|
| Ручная реализация | Decision Tree | Да | 0.9928 | 0.8305 | 0.8297 | 0.8294 | Контрольная реализация, написанная вручную |
| Ручная реализация | Random Forest | Да | 0.9932 | 0.8095 | 0.7247 | 0.7369 | Accuracy выше, но macro F1 ниже, чем у Decision Tree |
| YandexGPT | Decision Tree | Нет, после уточняющих промптов | 0.9930 | 0.8455 | 0.8384 | 0.8399 | Лучший результат по macro F1 среди всех запусков |
| GigaChat | Decision Tree | Нет, после уточняющих промптов | 0.9930 | 0.8310 | 0.8300 | 0.8290 | После включения Decision Tree результат близок к ручному baseline |

Если смотреть только на accuracy, все лучшие модели выглядят почти одинаково: около 0.993. Однако для этого датасета accuracy не дает полной картины, потому что крупные классы существенно преобладают над редкими.

По основной метрике macro F1 результаты распределились так:

| Место | Подход | Модель | Macro F1 |
|---:|---|---|---:|
| 1 | YandexGPT | Decision Tree | 0.8399 |
| 2 | Ручная реализация | Decision Tree | 0.8294 |
| 3 | GigaChat | Decision Tree | 0.8290 |
| 4 | GigaChat | Random Forest | 0.7370 |
| 5 | Ручная реализация | Random Forest | 0.7369 |

YandexGPT показала лучший итоговый macro F1-score, однако этот результат нельзя интерпретировать как однозначное превосходство LLM над ручной разработкой. Реализации отличаются деталями разбиения данных и параметрами моделей. Более корректный вывод состоит в том, что после нескольких уточняющих промптов YandexGPT смогла сгенерировать конкурентоспособный ML-пайплайн.

GigaChat после включения Decision Tree также получил результат, очень близкий к ручной реализации. Это говорит о том, что базовая структура сгенерированного приложения была пригодна, но первоначальные ошибки мешали корректному запуску и сравнению.

## 10. Анализ ошибок LLM

Ошибки, возникшие в ходе эксперимента, можно разделить на технические и методологические.

### 10.1. Технические ошибки

К техническим ошибкам относятся:

- жестко заданное неверное имя CSV-файла;
- некорректная логика сохранения лучшей модели;
- несогласованность ключей в словаре метрик;
- необходимость вручную уточнять структуру проекта.

Обе LLM изначально предположили, что файл датасета называется `IoT_Intrusion_Detection_Dataset.csv`. На практике файл назывался `IoT_Intrusion.csv`. Это показывает, что LLM может уверенно использовать правдоподобное, но неверное имя файла.

### 10.2. Методологические ошибки

Методологические ошибки оказались более важными. Особенно показателен случай GigaChat: модель пыталась определить целевой столбец по малому числу уникальных значений. Такой подход может работать для бинарных задач, но он ошибочен для многоклассовой классификации атак.

В результате GigaChat сначала предложил выбрать в качестве target column признаки вроде `HTTP`, `TCP`, `UDP`, `ICMP`, хотя правильный целевой столбец — `label`.

У YandexGPT методологическая проблема проявилась в выборе лучшей модели: сначала код пытался выбирать модель по accuracy, хотя в задаче с дисбалансом классов более корректно использовать macro F1-score.

### 10.3. Предупреждения scikit-learn

В обеих LLM-версиях возникали предупреждения:

```text
ConvergenceWarning: lbfgs failed to converge after 1000 iteration(s)
```

и:

```text
UndefinedMetricWarning: Precision is ill-defined and being set to 0.0 in labels with no predicted samples.
```

Первое предупреждение связано с Logistic Regression. Для большого многоклассового датасета стандартная логистическая регрессия без дополнительной настройки показала себя хуже деревьев решений.

Второе предупреждение связано с редкими классами. Некоторые классы представлены настолько малым числом объектов, что отдельные модели не предсказывают их ни разу. Это подтверждает выбор macro F1-score как основной метрики.

## 11. Ограничения эксперимента

У эксперимента есть несколько ограничений.

Во-первых, сравнение LLM-сгенерированного кода и ручной baseline-реализации не является абсолютно строгим сравнением моделей машинного обучения. Код отличается деталями реализации, поэтому небольшая разница в метриках может быть связана не только с качеством LLM, но и с параметрами пайплайна.

Во-вторых, в работе не проводился глубокий подбор гиперпараметров. Использовались базовые модели и параметры, достаточные для сравнения подходов генерации кода.

В-третьих, не решалась задача оптимизации под редкие классы. Для более качественного обнаружения редких атак можно было бы использовать балансировку классов, class weights, oversampling или отдельную бинарную постановку задачи «нормальный / вредоносный трафик».

В-четвертых, эксперимент проводился на одном датасете. Для более общего вывода о возможностях LLM нужно повторить такую проверку на нескольких наборах сетевого трафика.

## 12. Выводы

В ходе работы была проверена возможность использования российских LLM для генерации Python-приложений анализа сетевого трафика. Для эксперимента использовались YandexGPT и GigaChat. Обеим моделям передавался один и тот же русскоязычный промпт.

Обе LLM смогли сформировать общий ML-пайплайн: загрузка данных, первичный анализ, предобработка, обучение моделей, расчет метрик и сохранение результатов. Однако ни один вариант не оказался полностью рабочим с первого запуска.

YandexGPT допустила ошибки в технической логике: неверное имя файла, некорректное обращение к структуре словаря метрик и ошибки при выборе лучшей модели. После уточняющих промптов код был доведен до рабочего состояния. Лучшей моделью стала Decision Tree с macro F1-score 0.8399.

GigaChat также сначала указал неверное имя файла, а затем неправильно определил целевой столбец. После уточняющих промптов код был исправлен. После включения Decision Tree лучшей моделью GigaChat-версии стала Decision Tree с macro F1-score 0.8290.

Ручная baseline-реализация Decision Tree показала macro F1-score 0.8294. Таким образом, финальные LLM-версии оказались сопоставимы с ручной реализацией, но потребовали контроля, проверки и итеративной отладки.

Главный вывод работы: LLM можно использовать как инструмент ускорения разработки ML-приложений для анализа сетевого трафика, но не как полностью автономную замену разработчика. Наиболее рискованные ошибки возникают не в синтаксисе Python, а в методологии: выборе целевого столбца, выборе метрики, обработке дисбаланса классов и логике сравнения моделей.
